Hacking 4,000 Hospitals

Authentication flaws, exposed hospital data and the patient privacy at stake.

Hospital software holds some of the most private information a person can share. I found authentication flaws and exposed data in the software trusted to manage that care.

The software is e-Sushrut, a Hospital Management Information System (HMIS) developed and deployed by C-DAC. It manages patient information, hospital workflows and administrative processes in healthcare organizations.

I tested the installations at Bokaro General Hospital and AIIMS Patna. I reproduced the dashboard access, exposed activity counts and password-hashing issue at both. The findings led to three CVEs.

Bokaro’s login page had a link to its hospital dashboard. I opened it without signing in. The server sent back the dashboard page and its report information. The login HTML also exposed daily and total counts for outpatient visits, admissions, lab tests, prescriptions and pharmacy activity. And the password code used an odd-looking Java object string.

Patient privacy was the bigger concern

An HMIS sits at the center of hospital care. It handles patient information alongside registration, clinical workflows and administration. A failure in its access controls puts more than a dashboard at stake: it threatens the boundary around confidential personal and medical information.

The dashboard flaw let me reach report information without signing in. The login page disclosed hospital activity, and the password-hashing design allowed offline guessing if an attacker first captured a submitted hash, username and token. In a patient-data workflow, an unchecked report action could expose sensitive patient information. A compromised staff account could also expose the records that account is allowed to read.

Those are potential paths to patient-data exposure. The evidence shown here establishes dashboard access and operational-data disclosure; it does not establish that I retrieved individual patient records. The concern is what failures like these can mean in a system that handles them.

What came back

I read the response body to check what had loaded. It had the dashboard title, report names and report IDs. The reports covered outpatient visits, emergencies, prescriptions and lab work. An ID such as RPTDISPLAYNAME_REDACTED linked a report name to a specific part of the dashboard.

I repeated the request without a saved login. The server again returned HTTP 200 and a 274,427-byte page. Another request with Cookie: none gave the same result. The response set a new TID cookie, but I had not signed in.

The finding was that a visitor could get the dashboard page and its report information without signing in. CERT-In recorded this as weak authentication and session checks. What this exposed

I didn’t need to open the dashboard for this finding. The data was already in the login page’s HTML. Anyone who could open that page could read the string. No form submission was needed.

This exposed real patient activity data without authentication.

The page had a no-store header. That tells a browser or cache not to save the response. It does not stop a visitor from reading it. Hiding the statistics on screen would not fix this either. The server needs to leave internal counts out of the public login response and require a login before sending them.

The password code used a Java object string

CVE-2026-124645 · High · CVSS 4.0: 8.7
static/predictable value in client-side password hashing

The same JavaScript object had a field named SESSION_TOKEN. I searched for where it was used. Bokaro’s login HTML set the value in two places:

The [B@ prefix comes from Java. Object.toString() prints this kind of string for a byte array. [B means “byte array.” The @ is followed by the object’s hash code in hex. It does not print the bytes stored in the array.

The likely mistake was converting the byte-array object to text instead of encoding the random bytes inside it. The page received the object’s label as the login token. It wasn’t just an unwanted prefix; the token did not contain the array’s contents.

How the value reached the password hash

A hash turns some input into a fixed-length result. The same input gives the same result.

The page loaded ssoLogin.js. In its login routine, validate() called securePassword(). That function read the password and username, hashed them, then hashed the result with sessionToken. It put the final hash back into the password field. The code also set window.name = sessionToken.

The first hash becomes hex text: 128 characters for SHA-512 or 40 for SHA-1. The second hash takes that text followed by the token. If the password, username and token stay the same, the result stays the same too.

Why the object string mattered

The browser hashed the Java object label, rather than the byte array’s contents. Generating random bytes would not help if the page received the object label instead of those bytes. The challenge should carry the actual random bytes in an encoding such as Base64. Its security also depends on how the server creates it and checks it.

A login token can be public

A server can send a fresh random value with each login attempt. This is often called a nonce or challenge. The browser can read it. The server needs to remember which login attempt it belongs to, then check it when the form comes back.

Try both algorithms below. Keep the token the same or change it for each attempt to see what happens to the hash.

What an attacker would need

Suppose an attacker captures a user’s submitted hash, username and token. They can try a password guess on their own machine. They run the same two hash steps and compare the result with the captured hash. They do not need to send each guess to the hospital. This is offline password guessing.

A fresh token does not stop those guesses once the attacker has captured it too. It changes the hash for that attempt, but it does not make each guess slow. Both SHA-1 and SHA-512 are fast in this two-round setup.

The server should issue a fresh challenge, tie it to a login attempt, and check its expiry and reuse rules. Stored passwords also need a dedicated password-hashing function that makes guesses slow. Adding another fast hash in the browser does not replace these steps.
