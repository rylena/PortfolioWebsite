Hacking 4000 healthcare facilities

How I found three bugs in hospital software used across India, what the code did, and what the results showed.

I’ve been credited with three CVEs in a hospital management system used across 4,000+ healthcare facilities in India.

The software is called e-Sushrut. C-DAC builds it to manage patient records, registration and other hospital work. An August 2025 government announcement said it was used at more than 4,000 health facilities, including 17 AIIMS. I looked at two installations: Bokaro General Hospital and AIIMS Patna.

Bokaro’s login page had a link to its hospital dashboard. I opened it without signing in. The server sent back the dashboard page. The login page also included hospital activity counts and an odd value used by the password code.

I could open the dashboard without signing in

CVE-2026-124643 · improper authentication

Bokaro’s login page used the /AHIMSG5/hissso/ path. I checked its forms, JavaScript files and links. One link pointed to the dashboard:

The page gave me the full address and its URL parameters. I used that address in a separate request. I sent no username, password or saved login cookie.

What the URL parameters meant

Two values used Base64, a text encoding anyone can decode. NQ== means 5. SE1JUw== means HMIS. The dashboard HTML included both decoded values in hidden form fields.

These values told the server which dashboard to show. They did not prove who was asking. Anyone could copy a seatId into a URL. The server needed to check the caller’s login and access rights before returning the page.

What came back

I read the response body to check what had loaded. It had the dashboard title, report names and report IDs. The reports covered outpatient visits, emergencies, prescriptions and lab work. An ID such as RPTDISPLAYNAME_21_1_231 linked a report name to a specific part of the dashboard.

I repeated the request without a saved login. The server again returned HTTP 200 and a 274,427-byte page. Another request with Cookie: none gave the same result. The response set a new TID cookie, but I had not signed in.

Checking where the report data came from

The page loaded /HISUtilities/dashboard/js/dashboard.js. I read it to find how the reports got their data. Each report widget had a key with three parts: dashboard ID, section ID and report ID. The code used those IDs to send another request to the same server address:

Loading the dashboard page and loading a report’s rows were separate steps. I tried to build the report-data requests using GET_WIDGET_DATA. Those attempts redirected to /HISUtilities/security/Exception.jsp. I could also load a report template, but I did not get report rows from it.

I also changed hospitalCode to 10001 and 99999. Both replies had HTTP 200 and the same body length. That alone did not show access to another hospital’s data.

The finding was that a visitor could get the dashboard page and its report information without signing in. CERT-In recorded this as weak authentication and session checks. The fix needs to cover the dashboard page and each action it calls. The server should check the user’s login, hospital and role. It should get that identity from the login session, rather than trust an ID supplied in the URL.

What this exposed

I didn’t need to open the dashboard for this finding. The data was already in the login page’s HTML. Anyone who could open that page could read the string. No form submission was needed.

The counts showed hospital activity, including registrations, admissions, tests and prescriptions. They included daily and total figures. This string did not include patient names or medical histories.

The page had a no-store header. That tells a browser or cache not to save the response. It does not stop a visitor from reading it. Hiding the statistics on screen would not fix this either. The server needs to leave internal counts out of the public login response and require a login before sending them.

The password code used a Java object string

CVE-2026-124645 · static/predictable value in client-side password hashing

The same JavaScript object had a field named SESSION_TOKEN. I searched for where it was used. Bokaro’s login HTML set the value in two places:

The [B@ prefix comes from Java. Object.toString() prints this kind of string for a byte array. [B means “byte array.” The @ is followed by the object’s hash code in hex. It does not print the bytes stored in the array.

How the value reached the password hash

A hash turns some input into a fixed-length result. The same input gives the same result.

The page loaded ssoLogin.js. In its login routine, validate() called securePassword(). That function read the password and username, hashed them, then hashed the result with sessionToken. It put the final hash back into the password field. The code also set window.name = sessionToken.

The first hash becomes hex text: 128 characters for SHA-512 or 40 for SHA-1. The second hash takes that text followed by the token. If the password, username and token stay the same, the result stays the same too.

What I could tell from the saved tokens

The saved responses did not all have the same value. Bokaro’s first page had [B@71b8cc82. Another loginLogin response and the saved alternate-login responses had [B@3e0d430. Patna’s page had [B@16dba15a. These samples do not show that one value stayed fixed across every request or server.

CVE-2026-124645 describes a static, predictable value in the password-hashing code. My saved files show the values and how the browser used them. They do not show the full server logic. A [B@… string alone cannot show how random the value was. It also cannot show how often it changed or whether the server would accept it again.

A login token can be public

A server can send a fresh random value with each login attempt. This is often called a nonce or challenge. The browser can read it. The server needs to remember which login attempt it belongs to, then check it when the form comes back.

Try both algorithms below. Keep the token the same or change it for each attempt to see what happens to the hash.

What an attacker would need

Suppose an attacker captures a user’s submitted hash, username and token. They can try a password guess on their own machine. They run the same two hash steps and compare the result with the captured hash. They do not need to send each guess to the hospital. This is offline password guessing.

A fresh token does not stop those guesses once the attacker has captured it too. It changes the hash for that attempt, but it does not make each guess slow. Both SHA-1 and SHA-512 are fast in this two-round setup.

Replay means sending the captured hash back to the server to see whether it accepts it. I did not show a successful replay, a recovered password or an account takeover. The saved files show the browser’s calculations, not the server’s checks.

The server should issue a fresh challenge, tie it to a login attempt, and check its expiry and reuse rules. Stored passwords also need a dedicated password-hashing function that makes guesses slow. Adding another fast hash in the browser does not replace these steps.

What the other token fields did

I also read security.js. The form passed through sortandEncodebase64() before it was sent. This used another field that looked like a token:

abfhttf was a hidden field name. The code sorted the form fields, turned them into JSON, encoded that text with Base64, and put the result in this field. The dashboard used the name dbfhttf. Anyone could repeat those steps. Despite the name encryptBase64, the function had no secret encryption key.

I included this in the original report, but it did not receive a separate CVE among these three. It also did not prove a CSRF attack. CSRF means another site makes a user’s browser send an unwanted request. The login form had a separate Struts token, and I did not show a browser-based bypass of the other protections.

What differed between the two sites

The token pattern matched at both sites. The dashboard and activity-count leaks did not.

The Bokaro dashboard URL returned an error page on Patna. It had HTTP 200, but the body was only 1,011 bytes and asked the visitor to log in again. Patna’s login page also lacked the same HOSPITALS data. I did not confirm those two leaks there.
